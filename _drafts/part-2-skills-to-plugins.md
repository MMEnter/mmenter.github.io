# Part 2 of 6: From Skills to Plugins

*Series: Skills, Plugins, and Governance in the Enterprise*

## Brief

A plugin bundles skills with the things that make them act: connectors to company tools, hooks that run at key moments, commands, and agents. This is the "power" post, showing how a plugin turns a good workflow into something a whole team installs in one step. Walk through what each component contributes and why bundling matters for consistency. End on the tension: the more a plugin can do, the more it matters who wrote it and how it gets to people.

## Thesis

Skills tell Claude how to work. Plugins give it the reach to do the work, packaged so a team gets the same capability in one install.

## Outline

1. **Hook**
   - Recap in one line: Part 1 turned know-how into skills. But a skill can't open your ticketing system or run a check before Claude commits code.

2. **What a plugin contains**
   - **Skills:** the instructions (from Part 1).
   - **Commands:** named actions a user can invoke directly.
   - **Agents:** specialized sub-workers for focused tasks.
   - **MCP servers (connectors):** access to tools and data like ticketing, docs, CRM.
   - **Hooks:** actions that run automatically at points in Claude's workflow.
   - Keep each to two or three sentences with a practical example.

3. **Why bundling matters**
   - One install instead of a setup guide.
   - Everyone runs the same version of the workflow.
   - Updates reach the whole team at once.

4. **A plugin in practice (personal example)**
   - The workflow before.
   - The plugin you built or deployed.
   - The outcome for the team.

5. **Where plugins shine in the enterprise**
   - Onboarding, standard operating workflows, cross-tool processes, compliance-sensitive tasks done the same way every time.

6. **The tension (bridge to Part 3)**
   - Hooks run automatically. Connectors reach company data. Updates arrive on their own.
   - That power is the point, and it's also why it matters who wrote a plugin and how it reaches people.
